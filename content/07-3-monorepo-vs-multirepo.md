# 모노레포 vs 멀티레포

## 한 줄 정의

- **Monorepo(모노레포)**: 여러 프로젝트·서비스의 코드를 **하나의 Git 저장소** 안에 모두 넣고 관리하는 방식.
- **Multirepo(멀티레포, Polyrepo)**: 프로젝트·서비스마다 **별도의 Git 저장소**로 나눠서 관리하는 방식.

## 표로 비교

| | Monorepo | Multirepo |
|---|---|---|
| 코드 위치 | 하나의 저장소 안에 전부 | 저장소마다 따로 |
| 코드 공유 | 같은 저장소라 바로 참조·재사용 가능 | 패키지로 배포하거나 submodule 등으로 따로 연결해야 함 |
| 여러 프로젝트에 걸친 변경 | 커밋(PR) 하나로 한 번에 처리 가능 | 저장소마다 PR을 따로 올리고 조율해야 함 |
| 의존성 버전 | 보통 버전을 하나로 통일하기 쉬움 | 저장소마다 다른 버전을 쓸 수 있어 불일치 가능 |
| 접근 권한 | 저장소 단위라 세밀한 제어가 어려움 | 저장소별로 접근 권한을 분리하기 쉬움 |
| 저장소 크기·clone 속도 | 커질수록 무거워짐 | 저장소가 작아 가볍고 빠름 |
| 빌드/CI | 전용 도구 필요 (Bazel, Nx, Turborepo 등, 영향받는 부분만 빌드) | 저장소별로 독립적인 빌드/배포 파이프라인 |
| 대표 사례 | Google, Meta, 프론트엔드 모노레포 도구 생태계 | 대부분의 오픈소스 프로젝트, 마이크로서비스 아키텍처 |

## 장단점 요약

**Monorepo**
- 장점: 코드 공유가 쉽고, 여러 프로젝트를 아우르는 리팩토링을 한 커밋으로 처리할 수 있으며, 툴링·버전을 일관되게 유지하기 좋다.
- 단점: 저장소가 커질수록 clone·검색이 느려지고, 접근 권한을 세밀하게 나누기 어려우며, 전용 빌드 시스템이 사실상 필수가 된다.

**Multirepo**
- 장점: 저장소가 작아 가볍고, 팀·프로젝트별로 독립적인 배포 주기와 접근 권한을 가질 수 있다.
- 단점: 코드 공유가 번거롭고(패키지 배포 필요), 여러 저장소에 걸친 변경을 조율하기 어려우며, 저장소 간 의존성 버전이 어긋나기 쉽다.

## Submodule과의 관계

7-2에서 다룬 Submodule은 "저장소는 나누되(Multirepo), 서로 참조는 하고 싶다"는 절충안 중 하나다. Monorepo의 코드 공유 편의성 없이 Multirepo의 독립성을 유지한 채 연결만 해두는 방식이라, 완전한 대안이라기보다는 두 방식 사이의 타협에 가깝다. (다른 대안으로 `git subtree`나, 아예 패키지 매니저로 배포해서 참조하는 방법도 있다.)

## 명령어 치트시트 (7장 — 작업 공간 확장)

| 명령 | 설명 |
|---|---|
| `git worktree add <경로> <브랜치>` | 다른 브랜치를 별도 디렉토리에 체크아웃 |
| `git worktree list` | 연결된 worktree 목록 확인 |
| `git worktree remove <경로>` | worktree 제거 |
| `git submodule add <url> <경로>` | 서브모듈 추가 (`.gitmodules`에 기록) |
| `git clone --recurse-submodules <url>` | 서브모듈까지 함께 clone |
| `git submodule update --init --recursive` | 비어있는 서브모듈 채우기 |
| `git submodule update --remote` | 서브모듈을 원격 최신 커밋으로 갱신 |

(모노레포 vs 멀티레포 자체는 특정 git 명령이 아니라 저장소 구성 전략이라 별도 명령은 없다.)


## 한 줄 요약

Monorepo는 모든 코드를 한 저장소에 모아 공유와 일관성을 얻는 대신 규모가 커지는 문제가 있고, Multirepo는 저장소를 나눠 독립성과 접근 제어를 얻는 대신 코드 공유와 여러 저장소에 걸친 변경 조율이 번거로우며, Submodule은 그 사이의 절충안 중 하나다.
