# Rebase 개념과 규칙

## 한 줄 정의

- **Rebase**: 내 브랜치의 커밋들을 다른 브랜치(base) 위로 옮겨서 순서대로 다시 적용(replay)하는 것.
- 내용이 똑같아 보여도 실제로는 **새로운 커밋(새 해시)**이 생성된다 — 부모가 바뀌었기 때문.
- **황금률**: 이미 push해서 남이 받아간 커밋은 rebase하지 않는다.

## 표로 비교 — Rebase 전/후

| | Rebase 전 | Rebase 후 |
|---|---|---|
| 내 커밋의 부모 | 원래 갈라졌던 지점 | 옮겨간 base 브랜치의 최신 커밋 |
| 커밋 해시 | 그대로 | 전부 새로 계산됨 (내용이 같아도 다른 커밋 취급) |
| 히스토리 모양 | 갈래(diverge)진 그래프 | 일직선(linear) |

## Rebase가 실제로 하는 일

```
git rebase main    # (지금 브랜치를 main 위로)

1. 지금 브랜치와 main의 공통 조상(merge-base)을 찾는다
2. 공통 조상 이후, 지금 브랜치에만 있는 커밋들을 diff로 하나씩 뽑는다
3. main의 최신 커밋 위로 옮겨가서, 뽑아둔 diff들을 순서대로 재적용한다
4. 재적용될 때마다 새 해시로 커밋이 다시 만들어진다
```

즉 rebase는 "내 커밋들을 여러 번 cherry-pick해서 다른 브랜치 위에 순서대로 쌓는 것"과 원리가 같다.

## 왜 위험할 수 있는가

이미 push해서 다른 사람이 pull해 간 커밋을 rebase하면, 같은 작업인데 해시만 다른 커밋이 생긴다. 그러면 상대방의 로컬 히스토리와 내 원격 히스토리가 어긋나서, 다음 pull/push 때 충돌하거나 커밋이 중복으로 쌓이는 문제가 생긴다.

그래서 원칙은 하나다: **아직 나만 보고 있는 브랜치(push 안 했거나, push했어도 나만 쓰는 개인 브랜치)에서만 rebase한다.** 이미 공유된 브랜치(예: `main`)를 rebase하는 건 원칙적으로 하지 않는다.

## 한 줄 요약

Rebase는 내 커밋들을 다른 base 위로 옮겨 새 해시로 재생성하는 것이며, 히스토리를 일직선으로 만들어주는 대신 이미 공유된 커밋에는 절대 쓰지 않는 게 핵심 규칙이다.
