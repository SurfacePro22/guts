CHAPTER 1 · GIT VS GITHUB

01 Git과 GitHub, 뭐가 다른가

한 줄 정의

  • Git — 내 컴퓨터에서 동작하는 버전 관리 소프트웨어. 인터넷이 없어도 동작한다.
  • GitHub — Git 저장소를 올려두는 웹 서비스. PR·Issue·Actions 같은 부가 기능을 얹은 플랫폼(Microsoft 소유).

영상 편집에 비유하면 네 가지 개념이 깔끔하게 나뉜다. Git은 Premiere Pro(편집 프로그램), Repo는 프로젝트 파일(.prproj), Release는 거기서 뽑아낸 동영상(.mp4), GitHub은 YouTube다. 가장 흔한 혼동은 Git과 Repo를 같은 것으로 보는 것인데, Premiere Pro와 내 프로젝트 파일이 다른 것처럼 Git은 프로그램이고 Repo는 그 프로그램이 다루는 데이터다.

Git 세계영상 편집 세계정체어디에 있나
GitPremiere Pro도구(프로그램). 설치해서 쓴다내 컴퓨터에 설치된 git 실행 파일
Repo프로젝트 파일 (.prproj)작업물 + 편집 이력 전체. 언제든 다시 열어 고칠 수 있다프로젝트 폴더 안의 .git/
Release내보낸 동영상 (.mp4)특정 시점을 확정해 뽑아낸 배포용 결과물. 편집 이력은 없다태그(v1.0) + 빌드 파일·소스 압축본
GitHubYouTube올려서 공유하고 댓글·협업 기능을 얹는 서비스인터넷 서버

Git ≠ Repo — 프로그램과 프로젝트 파일은 다르다

비유의 한계 — YouTube에는 보통 완성된 동영상만 올리지만, GitHub에는 프로젝트 파일(repo) 자체를 통째로 올리고, 필요하면 그 옆에 동영상(Release)도 따로 게시한다. 즉 GitHub은 "프로젝트 파일 공유 + 영상 게시"를 함께 하는 YouTube에 가깝다. 또 Release의 태그는 repo 안에 기록되지만, 첨부 파일·릴리스 노트는 GitHub 기능이라 repo 밖(GitHub 서버)에 저장된다.

CHAPTER 2 · 저장소의 구조

02 저장소의 구조

2-1리포지터리의 5가지 영역

한 줄 정의

  • Workspace(작업 디렉토리) — 실제 파일을 수정하는 공간
  • Index(Staging Area) — add한 파일이 다음 커밋을 기다리는 대기 공간
  • Local Repo(로컬 저장소) — commit한 히스토리가 쌓이는 .git 내부 저장소
  • Upstream(원격 저장소) — GitHub 등 서버에 있는 저장소, 협업의 기준점
  • Stash — 커밋하지 않고 변경사항을 잠깐 치워두는 임시 서랍
영역위치담는 명령꺼내는 · 되돌리는 명령히스토리 보존
Workspace로컬 파일시스템직접 수정checkout, restore없음
Index.git/indexgit addgit reset없음
Local Repo.git 내부git commitgit log, checkout있음
Upstream원격 서버git pushfetch, pull있음(서버)
Stash.git/refs/stashgit stashstash pop/apply임시 스택
요약수정(Workspace) → 스테이징(Index) → 커밋(Local Repo) → 푸시(Upstream)가 기본 흐름이고, Stash는 그 흐름 중간에 잠깐 치워두는 임시 서랍이다.

2-2HEAD란? — HEAD, 브랜치, 커밋의 관계

한 줄 정의

  • HEAD — "지금 내가 어디에 있는지"를 가리키는 포인터. 대부분 브랜치를 가리키고, 그 브랜치가 다시 커밋을 가리킨다. 실체는 .git/HEAD 파일 하나뿐이다.
  • Detached HEAD — 브랜치가 아니라 커밋 해시를 직접 가리키는 상태. git checkout <커밋해시>처럼 브랜치명이 아닌 커밋으로 이동하면 발생한다.

CHAPTER 3 · 원격 저장소

03 원격 저장소

3-1원격과 프로토콜, Bare Repository란?

한 줄 정의

  • Remote(원격) — 내 로컬 저장소와 연결된, 다른 위치의 Git 저장소를 가리키는 이름표. 기본 이름은 origin, 원본 프로젝트를 따로 가리킬 땐 관례상 upstream을 쓴다.
  • 프로토콜 — 원격 저장소에 접속하는 방식. HTTPS, SSH, 로컬 파일시스템 File(file://), Git 고유의 Git(git://) 프로토콜이 있다.
  • Bare Repository — 작업 디렉토리 없이 .git 내부 내용만 있는 저장소. 사람이 직접 수정하는 곳이 아니라 서로 주고받는 서버용 저장소.

일반 저장소의 .git/ 폴더 안에 있던 내용물이, bare 저장소에서는 워킹 트리 없이 최상위 폴더에 그대로 펼쳐진다.

my-repo.git/          # bare 저장소 (자체가 곧 .git 내용물)
├── HEAD
├── config
├── description
├── hooks/
├── info/
├── objects/
└── refs/

핵심은 세 가지다. HEAD는 ref: refs/heads/main 한 줄이 전부이며, clone하는 사람이 옵션 없이 git clone만 쳤을 때 받을 기본 브랜치를 정한다 (git symbolic-ref HEAD refs/heads/develop로 변경). objects/에는 blob(파일 내용)·tree(디렉터리 구조)·commit(스냅샷+부모+메시지) 세 종류가 objects/ab/cdef... 형태로 쌓이고, 많아지면 git gc가 .pack 파일로 압축한다. refs/는 refs/heads/main처럼 파일 하나가 커밋 해시 한 줄만 담은 이름표다.

요약Remote는 다른 위치의 저장소를 가리키는 이름표, 프로토콜은 접속 방법(HTTPS/SSH/File/Git)이고, Bare Repository는 워킹 트리 없이 .git 내용물만 최상위에 펼쳐진 서버용 저장소다.

git remote add origin <url> 같은 명령은 새 데이터베이스가 아니라 Local 설정(.git/config)에 기록되는 것뿐이다.

[remote "origin"]
    url = git@github.com:me/repo.git
    fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
    remote = origin
    merge = refs/heads/main

branch.main.remote / branch.main.merge가 바로 "내 main은 origin의 main을 추적한다"는 설정이며, 다음 절(Fetch vs Pull)의 근거가 된다.

요약git config는 System → Global → Local 순으로 좁은 범위가 우선하는 설정 저장소이고, 사용자 정보부터 원격 주소·브랜치 추적까지 전부 여기에 저장된다.

3-3Fetch vs Pull 차이 (origin/main vs origin main)

한 줄 정의

  • Fetch — 원격의 새 커밋·오브젝트를 로컬로 받아오기만 하고, 내 로컬 브랜치는 건드리지 않는다.
  • Pull — Fetch + 받아온 내용을 로컬 브랜치에 merge(또는 rebase)까지 자동 수행한다.
  • origin/main — 로컬에 저장된 원격 추적 브랜치. 마지막 fetch 시점의 스냅샷을 가리키는 로컬 포인터.
  • origin main(슬래시 없음) — git push origin main처럼 명령 인자로 쓰인 것. 원격 서버 안의 실제 main 브랜치.
FetchPull
하는 일원격의 새 커밋·오브젝트만 받아옴Fetch + 로컬 브랜치에 merge/rebase까지
건드리는 것objects/, refs/remotes/origin/*위 전부 + refs/heads/<브랜치>, 워킹 트리
내 로컬 브랜치그대로 유지 (안전)변경됨 (merge 커밋 또는 rebase)
충돌 가능성없음있음
요약Fetch는 원격 정보를 받아만 오고, Pull은 거기에 로컬 브랜치 반영까지 더한 것이며, origin/main은 로컬 포인터인 반면 origin main은 원격 서버의 실제 브랜치를 가리키는 명령 인자다.

CHAPTER 4 · 변경사항 이식하기

04 변경사항 이식하기

4-1Diff와 Hunk (.. vs ... 차이), Patch 개념

한 줄 정의

  • Diff — 두 상태(파일·커밋·브랜치) 사이의 차이를 줄 단위로 보여주는 것.
  • Hunk — diff 안에서 변경된 부분을 묶은 덩어리 하나. @@ -a,b +c,d @@로 시작하는 구간.
  • Patch — diff 결과를 파일로 저장해, 다른 저장소·다른 시점에 그대로 적용할 수 있게 만든 것.
TL;DR — git diff A..B는 git diff A B와 완전히 같습니다. A와 B의 최종 스냅샷을 그냥 맞대고 비교합니다. git diff A...B는 두 브랜치가 갈라진 지점(merge-base)을 기준으로 삼아, B가 그 이후 새로 만든 변경만 보여줍니다.

실습으로 재현하기

터미널에 그대로 붙여넣으면 아래 그림과 똑같은 저장소가 만들어집니다. 공통 조상에서 갈라진 뒤, master는 파일을 하나 고치고 feature는 새 파일을 하나 추가합니다.

# 저장소 초기화 + 공통 조상 커밋 2개
git init demo && cd demo
echo "line1" > file.txt && git add . && git commit -m "C1: init"
echo "line2" >> file.txt && git commit -am "C2: add line2"

# feature 브랜치: 여기서부터 갈라짐, 새 파일 추가
git checkout -b feature
echo "feature-A" > feature.txt && git add . && git commit -m "C3: add feature.txt"
echo "feature-B" >> feature.txt && git commit -am "C4: update feature.txt"

# master로 돌아와 그동안 file.txt를 따로 수정
git checkout master
echo "line3-main" >> file.txt && git commit -am "C5: add line3"

이제 같은 두 브랜치를 점 개수만 바꿔서 비교해 봅니다. 실제로 실행한 결과입니다.

주의: diff의 A...B는 "비교 기준점 자체를 공통 조상으로 바꿔서 B 하나만 보는 것"이고, log의 A...B는 "A와 B 각각의 도달 가능 커밋 집합끼리 대칭차집합을 구하는 것"이라 동작 원리 자체가 다릅니다. 같은 점 표기라도 diff와 log에서 계산 기준이 다르다는 점을 구분해서 기억해야 합니다.

Cherry-pick(다음 절)도 내부적으로는 "특정 커밋의 diff를 patch처럼 뽑아서 현재 브랜치 위에 적용"하는 것과 같은 원리다.

요약Diff는 차이 전체, Hunk는 그 안의 변경 덩어리 하나이며, A..B는 있는 그대로의 비교, A...B는 공통 조상 기준 비교(log에서는 양방향 차집합)라는 게 핵심 차이다. Patch는 그 diff를 파일로 저장해 다른 곳에 적용하는 것이다.

4-2Cherry-pick (개념 + 충돌 해결)

한 줄 정의

  • Cherry-pick — 다른 브랜치에 있는 커밋 하나(또는 몇 개)만 골라서, 그 변경사항을 지금 브랜치 위에 새로운 커밋으로 복사해오는 것. 원리는 4-1의 patch와 같다 — diff를 뽑아 현재 브랜치에 적용하고, 새 해시로 다시 커밋한다.

충돌 해결 절차

# 2. 해결한 파일을 스테이징

# 3. cherry-pick 계속 진행

요약Cherry-pick은 커밋 하나의 diff를 patch처럼 뽑아 다른 브랜치 위에 새 커밋으로 복사하는 것이며, 충돌이 나면 merge 충돌과 같은 방식(마커 편집 → add → --continue)으로 해결한다.

CHAPTER 5 · REBASE

05 Rebase

5-1Rebase 개념과 규칙

한 줄 정의

  • Rebase — 내 브랜치의 커밋들을 다른 브랜치(base) 위로 옮겨서 순서대로 다시 적용(replay)하는 것.
  • 내용이 똑같아 보여도 실제로는 새로운 커밋(새 해시)이 생성된다 — 부모가 바뀌었기 때문.
  • 황금률 — 이미 push해서 남이 받아간 커밋은 rebase하지 않는다.

Before — 분기됨

After — main 뒤로 재배치(replay)

Rebase가 실제로 하는 일

git rebase main    # (지금 브랜치를 main 위로)

1. 지금 브랜치와 main의 공통 조상(merge-base)을 찾는다
2. 공통 조상 이후, 지금 브랜치에만 있는 커밋들을 diff로 하나씩 뽑는다
3. main의 최신 커밋 위로 옮겨가서, 뽑아둔 diff들을 순서대로 재적용한다
4. 재적용될 때마다 새 해시로 커밋이 다시 만들어진다

즉 rebase는 "내 커밋들을 여러 번 cherry-pick해서 다른 브랜치 위에 순서대로 쌓는 것"과 원리가 같다.

왜 위험할 수 있는가 — 이미 push해서 다른 사람이 pull해 간 커밋을 rebase하면, 같은 작업인데 해시만 다른 커밋이 생긴다. 그러면 상대방의 로컬 히스토리와 내 원격 히스토리가 어긋나서, 다음 pull/push 때 충돌하거나 커밋이 중복으로 쌓인다. 원칙은 하나다: 아직 나만 보고 있는 브랜치에서만 rebase한다.
요약Rebase는 내 커밋들을 다른 base 위로 옮겨 새 해시로 재생성하는 것이며, 히스토리를 일직선으로 만들어주는 대신 이미 공유된 커밋에는 절대 쓰지 않는 게 핵심 규칙이다.

5-2Interactive Rebase (pick/squash/fixup/drop/reorder)

한 줄 정의

  • Interactive Rebase — git rebase -i <base>를 실행하면 에디터가 열리고, 재적용될 커밋 목록을 보여주면서 각 커밋을 어떻게 처리할지 직접 고를 수 있는 방식.
명령역할
pick그대로 사용 (기본값)
reword적용하되 커밋 메시지만 다시 씀
edit적용한 뒤 멈춰서 내용을 직접 고칠 기회를 줌
squash바로 위 커밋과 합치고, 두 메시지를 합쳐서 편집
fixup바로 위 커밋과 합치되 이 커밋의 메시지는 버림
drop이 커밋을 통째로 제거
(줄 순서 바꾸기)목록에서 줄 위치를 옮기면 곧 커밋 적용 순서 변경(reorder)

에디터 화면 읽는 법

git log는 최신 커밋이 위에 오지만, interactive rebase 목록은 반대로 오래된 커밋이 위에 온다 (위에서부터 순서대로 재적용되기 때문). 이 방향이 헷갈려서 실수로 순서를 잘못 바꾸는 경우가 많으니 주의.

pick a1b2c3 feat: add subtract function
pick d4e5f6 debug: add print statement
pick 789abc fix: correct typo in subtract docstring
pick bcdef1 test: add unit tests
pick 234567 feat: add divide function

위 목록을 아래처럼 바꾸면, 디버그용 커밋은 사라지고 오타 수정 커밋은 바로 위 커밋에 조용히 합쳐진다.

pick a1b2c3 feat: add subtract function
drop d4e5f6 debug: add print statement
fixup 789abc fix: correct typo in subtract docstring
pick bcdef1 test: add unit tests
pick 234567 feat: add divide function

참고: --autosquash — 커밋 메시지 앞에 fixup!이나 squash!를 붙여 커밋해두면(git commit --fixup=<해시>), git rebase -i --autosquash <base> 실행 시 그 커밋들이 자동으로 대상 커밋 바로 아래에 배치된 채로 에디터가 열린다.

요약Interactive rebase는 커밋 목록을 열어 pick/reword/edit/squash/fixup/drop과 줄 순서 변경으로 히스토리를 재구성하는 것이며, 목록이 git log와 반대로 오래된 순서(위→아래)로 나열된다는 점을 기억해야 한다.

5-3Merge vs Rebase 비교

한 줄 정의

  • Merge — 두 브랜치의 기존 커밋을 그대로 둔 채, 두 부모를 가진 새로운 "머지 커밋"을 만들어 합치는 것.
  • Rebase — 내 커밋들을 다른 브랜치 위로 옮겨 새 해시로 재생성해서, 히스토리를 일직선으로 만드는 것.

Merge — 히스토리 보존

Rebase — 히스토리 선형화

MergeRebase
결과두 부모를 가진 merge commit이 새로 생김기존 커밋들이 새 해시로 재생성됨
기존 커밋그대로 보존 (해시 안 바뀜)재작성됨 (해시 바뀜)
히스토리 모양갈래졌다 다시 합류일직선(linear)
충돌 해결보통 한 번 (merge 시점에 몰아서)커밋마다 나눠서 여러 번 날 수 있음
공유 브랜치안전위험 (황금률 위반)

git log --graph --oneline --all로 확인하면, merge는 갈라졌다 합쳐지는 * 노드가 보이고 rebase는 애초에 갈라진 적 없던 것처럼 일직선으로 이어진다.

요약Merge는 기존 커밋을 건드리지 않고 두 히스토리를 있는 그대로 합치는 안전한 방법이고, Rebase는 히스토리를 깔끔한 일직선으로 만들어주는 대신 커밋을 재작성하므로 이미 공유된 브랜치에는 쓰면 안 된다.

CHAPTER 6 · 되돌리기 전략

06 되돌리기 전략

한 줄 정의

  • Reset — HEAD(와 브랜치 포인터)를 다른 커밋으로 옮기는 것. --soft/--mixed/--hard 옵션에 따라 Index·Workspace까지 건드리는 범위가 다르다.
  • Revert — 특정 커밋의 변경을 취소하는 새 커밋을 추가하는 것. 히스토리를 지우지 않고 거꾸로 되돌린다.
  • Reflog — HEAD가 가리켰던 위치들의 로컬 기록. reset/rebase 등으로 "사라진 것처럼 보이는" 커밋을 되찾는 안전망.
--soft--mixed (기본값)--hard
HEAD·브랜치이동이동이동
Index그대로 유지초기화(unstage)초기화
Workspace그대로 유지그대로 유지되돌린 커밋 상태로 덮어씀
쓰는 상황커밋만 취소하고 다시 커밋커밋·스테이징 취소, 수정 내용은 유지완전히 되돌리기 (위험, 유실 가능)
ResetRevert
방식브랜치 포인터를 과거로 이동취소하는 새 커밋을 추가
기존 히스토리그 이후 커밋들이 브랜치에서 빠짐그대로 보존, 새 커밋만 하나 늘어남
공유 브랜치위험 (히스토리 재작성)안전 (기존 커밋 안 건드림)
쓰는 상황아직 push 안 한 로컬 실수 정리이미 push되어 남들도 받아간 커밋 취소

Reflog로 복구하기

reset --hard나 rebase 때문에 커밋이 브랜치에서 떨어져 나가도, 실제 커밋 데이터는 바로 지워지지 않는다. git reflog가 HEAD의 이동 기록을 전부 남겨두기 때문에, 되돌리기 전 해시를 찾아 복구할 수 있다.

git reflog
# 예: a1b2c3d HEAD@{0}: reset: moving to HEAD~2
#     789abcd HEAD@{1}: commit: fix bug

git reset --hard 789abcd    # reflog에서 찾은 해시로 복구
단, reflog는 로컬 저장소에만 있고(원격엔 없음), 기본적으로 일정 기간(기본 90일)이 지나면 만료되어 사라진다는 한계가 있다.
요약Reset은 포인터를 옮겨 히스토리 자체를 바꾸는 것(soft/mixed/hard로 반영 범위가 다름)이고, Revert는 새 커밋으로 안전하게 취소하는 것이며, Reflog는 이런 작업으로 사라진 것처럼 보이는 커밋도 되찾을 수 있는 로컬 안전망이다.

git reset --hard <커밋>
포인터+Index+Workspace 전부 되돌림 (위험)
git revert <커밋>

git reset --hard <reflog 해시>

7-1Stash 대신 Worktree를 써야 하는 이유

한 줄 정의

  • Worktree — 하나의 .git 저장소를 공유하면서, 서로 다른 브랜치를 동시에 체크아웃할 수 있는 독립된 작업 디렉토리를 추가로 만드는 기능.
Stash로 브랜치 전환Worktree 사용
지금 하던 작업임시로 치워둠 (pop 잊으면 유실 위험)그대로 유지됨 (다른 디렉토리)
전환 방법stash → checkout → 나중에 popgit worktree add <경로> <브랜치>
동시 작업한 번에 한 브랜치만여러 브랜치를 서로 다른 폴더에서 동시에
실수 위험stash가 쌓이면 헷갈림, pop 충돌 가능애초에 전환할 필요가 없어 줄어듦
 
git worktree add ../hotfix hotfix-branch   # ../hotfix에 hotfix-branch를 체크아웃
cd ../hotfix                               # 별도 디렉토리 — 원래 작업 디렉토리는 그대로

git worktree list                          # 연결된 worktree 목록 확인
git worktree remove ../hotfix              # 다 쓰면 제거

AI 에이전트와 함께 쓰기 좋은 이유

Claude Code 같은 AI 코딩 에이전트를 여러 개 동시에 돌리거나, 에이전트가 작업하는 동안 다른 작업을 병행하고 싶을 때 worktree가 잘 맞는다. 에이전트마다 독립된 폴더 + 독립된 브랜치를 주면 서로 파일을 건드릴 일이 없기 때문이다. 다만 브랜치 하나는 worktree 하나에만 체크아웃 가능해서 미리 브랜치를 나눠줘야 하고, node_modules 같은 의존성은 워크트리마다 따로 설치해야 한다는 한계도 같이 알아둬야 한다.

요약Stash는 지금 작업을 임시로 치워두고 브랜치를 전환하는 방식이라 유실 위험이 따르지만, Worktree는 같은 저장소를 공유하는 별도 디렉토리에서 다른 브랜치를 동시에 작업할 수 있어 전환 자체가 필요 없어진다.

7-2Submodule이란?

한 줄 정의

  • Submodule — 한 Git 저장소 안에 다른 Git 저장소를 통째로 포함시켜서, 독립적으로 버전 관리되는 하위 프로젝트로 참조하는 기능. 부모 저장소는 실제 코드가 아니라 "이 경로에는 이 커밋 해시 시점의 서브모듈이 있다"는 포인터 하나만 기록한다.
명령역할
git submodule add <url> <경로>새 서브모듈 추가 (.gitmodules에 기록)
git clone --recurse-submodules <url>부모 clone 시 서브모듈 내용까지 함께 받기
git submodule update --init --recursive이미 clone한 뒤, 비어있는 서브모듈 폴더 채우기
git submodule update --remote서브모듈을 그 자신의 원격 최신 커밋으로 갱신
(서브모듈 폴더 안에서 직접 커밋/푸시)완전히 독립된 저장소라서 그 안에서 따로 커밋해야 함

서브모듈 폴더를 처음 clone 직후 열어보면 비어있는 경우가 많다 — 부모 저장소는 코드가 아니라 해시만 알고 있고, 실제 코드는 git submodule update --init으로 그 해시에 맞춰 따로 받아와야 채워지기 때문이다.

요약Submodule은 부모 저장소 안에 다른 저장소를 특정 커밋 시점으로 고정해서 참조하는 기능이며, 실제 코드가 아니라 커밋 해시 하나만 기록되므로 clone 이후 별도로 초기화·갱신해줘야 한다.

7-3모노레포 vs 멀티레포

한 줄 정의

  • Monorepo(모노레포) — 여러 프로젝트·서비스의 코드를 하나의 Git 저장소 안에 모두 넣고 관리하는 방식.
  • Multirepo(멀티레포, Polyrepo) — 프로젝트·서비스마다 별도의 Git 저장소로 나눠서 관리하는 방식.

Monorepo — 저장소 1개

Project A
Project B
Project C

Multirepo — 저장소 여러 개

Repo A
자체 .git
Repo B
자체 .git
Repo C
자체 .git
MonorepoMultirepo
코드 공유같은 저장소라 바로 참조·재사용패키지 배포 또는 submodule 등으로 연결
여러 프로젝트 변경커밋(PR) 하나로 한 번에 처리저장소마다 PR을 따로 올리고 조율
접근 권한저장소 단위라 세밀한 제어 어려움저장소별로 분리하기 쉬움
저장소 크기커질수록 무거워짐작고 가벼움
빌드/CI전용 도구 필요 (Bazel, Nx, Turborepo 등)저장소별 독립 파이프라인
대표 사례Google, Meta, 프론트엔드 모노레포 생태계대부분의 오픈소스, 마이크로서비스

7-2의 Submodule은 "저장소는 나누되(Multirepo), 서로 참조는 하고 싶다"는 절충안 중 하나다. Monorepo의 코드 공유 편의성 없이 Multirepo의 독립성을 유지한 채 연결만 해두는 방식이라, 완전한 대안이라기보다는 두 방식 사이의 타협에 가깝다.

요약Monorepo는 모든 코드를 한 저장소에 모아 공유와 일관성을 얻는 대신 규모가 커지는 문제가 있고, Multirepo는 저장소를 나눠 독립성과 접근 제어를 얻는 대신 코드 공유와 변경 조율이 번거로우며, Submodule은 그 사이의 절충안 중 하나다.
